## ADR-001. 세션 쿠키 인증 및 MySQL `sessions` 테이블 관리

- **관련 요구사항**: REQ-001, REQ-002, REQ-003, REQ-112
- **상태**: 결정

### 배경
- 프론트엔드는 빌드 없는 Vanilla JavaScript다 (CLAUDE.md §1). 토큰을 클라이언트에서 저장하고 갱신하는 코드는 복잡도가 높다.
- 토큰을 `localStorage`에 두면 XSS로 탈취될 수 있다.
- 로그아웃 시 서버에서 인증을 즉시 끊어야 한다 (REQ-002).

### 결정
1. **인증 방식**: 서버 측 세션을 쓰고, 클라이언트에는 `HttpOnly`, `SameSite=Lax` 쿠키만 둔다. `Secure` 속성은 HTTPS 환경에서 켜며, 개발 환경(HTTP)에서는 끈다. 세부 값은 `.env`에서 주입한다.
2. **저장소**: MySQL `sessions` 테이블을 쓴다 (데이터 설계서 §3.6).
   - 쿠키에는 `secrets.token_urlsafe(32)`로 만든 무작위 토큰 원문을 넣는다.
   - DB의 `id`에는 토큰의 SHA-256 다이제스트(`BINARY(32)`)만 저장한다. DB가 노출되어도 유효한 세션 토큰은 노출되지 않는다.
   - 수명: 로그인 후 14일 절대 만료. 슬라이딩 연장은 하지 않는다. **이 수명은 기본값이며 사용자 확인이 필요하다.**
3. **무효화**: 로그아웃은 해당 행을 삭제한다. 계정 삭제 시 `ON DELETE CASCADE`로 모든 세션이 함께 삭제된다.
4. **만료 정리**: 1차에서는 인증 조회 시 `expires_at > UTC_TIMESTAMP(3)` 조건으로만 걸러낸다. 누적 행의 배치 삭제는 후속 과제로 둔다.

### 검토한 대안
| 대안 | 장점 | 단점 | 판정 |
| :--- | :--- | :--- | :--- |
| JWT (Stateless) | DB 조회 없음 | 발급 후 무효화가 어렵다. 로그아웃에 블랙리스트가 필요하다. 클라이언트에서 토큰 관리가 필요하다. | 기각 |
| 메모리 세션 | 구현이 가장 단순하다 | 프로세스 재시작 시 세션이 사라진다. 워커를 여러 개 띄우면 공유되지 않는다. | 기각 |
| Redis 세션 | 빠르고 만료 관리가 쉽다 | 현재 스택에 없는 컨테이너를 추가해야 한다. 1차 규모에 과하다. | 보류 (필요 시 재검토) |
| **DB `sessions` 테이블** | 기존 MySQL을 재사용한다. 재시작 후에도 유지된다. 계정 삭제 시 CASCADE로 정리된다. | 요청마다 DB 조회가 한 번 추가된다 | **채택** |

### 결과
- 인증 요청마다 `sessions` 조회가 한 번 발생한다. PK 조회라 p95 300ms 목표(REQ-102)에 영향은 작다.
- CSRF: `SameSite=Lax`는 cross-site POST에서 쿠키를 보내지 않으므로 기본 방어가 된다. 다만 같은 사이트의 다른 서브도메인은 막지 못한다. 현재 단일 도메인 구성이므로 1차에서는 별도 CSRF 토큰을 두지 않는다. 이 판단은 배포 구조가 바뀌면 재검토한다.

## ADR-002. 비밀번호 해시 알고리즘: bcrypt

- **관련 요구사항**: REQ-001, REQ-110, REQ-111
- **상태**: 결정

### 배경
- REQ-110은 평문 저장을 금지하고, bcrypt 또는 argon2 중 하나를 쓰도록 했다.
- 프로젝트 규모는 소규모 단어장 서비스이며, 의존성을 단순하게 유지하는 것이 중요하다.

### 결정
1. **알고리즘**: **bcrypt**를 쓴다.
2. **비용 계수(cost factor)**: 12를 기본값으로 둔다 (`.env`에서 조정 가능하게 한다). **제안 값이며 구현 시 벤치마크로 확인한다.**
3. **입력 길이 제한**: bcrypt는 입력의 **앞 72바이트까지만** 사용하고 나머지는 조용히 무시한다. 따라서 Pydantic 검증에서 UTF-8 기준 **72바이트 이하**인 비밀번호만 허용한다 (REQ-001 반영). 이를 빼먹으면 긴 비밀번호의 뒷부분이 검증 없이 무시되는 문제가 생긴다.
4. **저장 형식**: `password_hash VARCHAR(255)`에 bcrypt 결과 문자열 전체를 저장한다 (60자, 여유 확보).

### 검토한 대안
| 대안 | 장점 | 단점 | 판정 |
| :--- | :--- | :--- | :--- |
| **bcrypt** | 오래 검증되었고 널리 쓰인다. 설치가 가볍다. 비용 계수로 강도를 조절한다. | 메모리 소비가 작아 GPU 공격에 argon2보다 약하다. 72바이트 제한이 있다. | **채택** |
| argon2id | 메모리 하드 함수라 현재 권장 알고리즘이다. 길이 제한이 없다. | 네이티브 의존성이 필요하다. 이 규모에서는 이득이 제한적이다. | 보류 (사용자 선택 결과 bcrypt 채택) |
| PBKDF2 | 표준 라이브러리로 구현 가능하다 | 같은 비용에서 bcrypt보다 약하다고 평가된다 | 기각 |

### 결과
- 해시 비교는 `bcrypt.checkpw`로 수행하며, 사용자 존재 여부와 무관하게 해시 비교가 항상 한 번 실행되도록 해서 응답 시간으로 계정 존재를 추측하지 못하게 한다 (REQ-002).
- 향후 argon2id로 바꾸려면 해시 재생성(로그인 시 점진적 재해시)이 필요하다. 해시 문자열의 접두사(`$2b$`)로 알고리즘을 구분할 수 있다.

## ADR-003. 단어 검색: 접두사 인덱스 전략, 뜻 검색 제외

- **관련 요구사항**: REQ-009, REQ-113, REQ-103
- **상태**: 결정

### 배경
- 원래 REQ-009는 "표제어 또는 뜻의 부분 일치 검색"이었다.
- `LIKE '%keyword%'`는 B-Tree 인덱스를 쓸 수 없어서 행을 전부 읽는다.
- 검색 범위는 항상 한 단어장 안으로 제한된다. 단어장 하나의 단어 수는 대략 수백~1,000개 규모다 (REQ-103 기준).

### 결정
1. **표제어 검색은 접두사 일치**로 한다: `WHERE wordbook_id = ? AND term LIKE 'keyword%'`.
2. **인덱스**: 기존 `UNIQUE KEY uk_words_wordbook_term (wordbook_id, term)`이 이 쿼리를 커버한다. 별도 인덱스를 추가하지 않는다.
3. **대소문자 무시**: 콜레이션 `utf8mb4_0900_ai_ci`가 처리한다. 검색어를 따로 변환하지 않는다.
4. **뜻(meaning) 검색은 1차에서 제외**한다.
5. **LIKE 이스케이프**: 검색어의 `%`, `_`, `\`는 이스케이프한다. 값은 바인딩 파라미터로 전달한다 (REQ-113).
6. **페이징**: 기본 20건, OFFSET 방식을 쓴다. 단어 수가 적어 OFFSET 비용은 무시할 수준이다.

### 검토한 대안
| 대안 | 장점 | 단점 | 판정 |
| :--- | :--- | :--- | :--- |
| **접두사 일치 + UNIQUE 인덱스** | 인덱스를 그대로 활용한다. 추가 비용이 없다. | `%중간%` 검색이 안 된다. | **채택** |
| `%keyword%` (부분 일치) | 사용성이 가장 좋다 | 인덱스를 못 쓰고 단어장 전체를 스캔한다. 규모가 커지면 느려진다. | 기각 (1차) |
| FULLTEXT (ngram 파서) | 부분 일치와 CJK 검색을 지원한다 | 인덱스 추가, 파서 설정, 관리 비용이 든다. 1차 규모에 과하다. | 보류 (필요 시 재검토) |

### 뜻 검색을 제외한 배경
- 뜻(`meaning`)은 자유 텍스트라서 접두사 인덱스가 도움이 되지 않는다. 포함하려면 부분 일치나 FULLTEXT가 필요하다.
- 접두사 검색으로 확정하면서 뜻 검색은 인덱스 전략과 함께 자연스럽게 빠졌다. 사용자 요구가 명확하지 않아 별도 확인을 거쳤다.
- **재검토 조건**: 사용자 피드백에서 뜻 검색 요구가 나오면, FULLTEXT ngram 인덱스를 추가하는 방향으로 ADR을 새로 작성한다. 데이터 설계서 F4에 기록했다.

### 결과
- 1차 검색 성능은 인덱스로 보장된다.
- 뜻 검색 요구가 있으면 기능 누락이 된다. 이 리스크는 F4로 추적한다.
