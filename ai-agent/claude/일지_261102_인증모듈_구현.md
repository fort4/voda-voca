## 4. 보안 정책

### 4.1 세션 토큰 저장 (ADR-001)
- 쿠키에는 `secrets.token_urlsafe(32)`로 만든 무작위 토큰 원문을 담습니다.
- DB `sessions.id`에는 토큰의 SHA-256 다이제스트(`BINARY(32)`)만 저장합니다. DB가 노출되어도 유효한 세션 토큰이 복원되지 않습니다.
- 테스트 `test_login_stores_only_token_digest`가 이 동작을 확인합니다.

### 4.2 쿠키 속성
- `HttpOnly`: JavaScript에서 읽을 수 없습니다 (XSS로 인한 토큰 탈취 방지).
- `SameSite=Lax`: 교차 사이트 POST에 쿠키가 실리지 않습니다. CSRF의 기본 방어입니다. 같은 사이트의 다른 서브도메인은 막지 못하므로, 배포 구조가 바뀌면 재검토합니다 (ADR-001 결과).
- `Path=/`, `Max-Age=1209600`(14일).
- `Secure`: 기본값 `false` (로컬 HTTP 개발). `.env`의 `COOKIE_SECURE=true`로 HTTPS 배포 시 켭니다.
- 쿠키 삭제(로그아웃)는 설정 시와 같은 속성을 씁니다. 그래야 브라우저가 쿠키를 지웁니다.

### 4.3 로그인 시 새 토큰 발급
- 로그인할 때마다 새 토큰을 만듭니다. 이전 토큰을 재사용하지 않으므로 세션 고정 공격을 막습니다.

### 4.4 계정 존재 여부 비노출
- 틀린 비밀번호와 존재하지 않는 이메일 모두 같은 401 본문(`이메일 또는 비밀번호가 올바르지 않습니다.`)을 반환합니다.
- 존재하지 않는 이메일에서도 더미 bcrypt 검증을 한 번 실행합니다 (`get_dummy_hash`). 응답 시간으로 계정 존재를 추측하지 못하게 하기 위함입니다 (REQ-002).
- 더미 해시는 처음 필요할 때 한 번만 만들고 캐시합니다.

### 4.5 비밀번호 해시와 길이 제한 (ADR-002)
- bcrypt로 해시합니다. cost는 12(운영), 테스트에서는 4입니다.
- bcrypt 5.x는 72바이트를 초과하면 `ValueError`를 던집니다. 그래서 두 곳에서 방어합니다.
  - 입력 단계: Pydantic 검증이 UTF-8 기준 72바이트 초과를 422로 거부합니다.
  - 검증 단계: `_verify_sync`가 72바이트 초과 입력을 불일치로 처리하고, 깨진 해시 형식도 예외 없이 불일치로 처리합니다.
- 해시 계산과 검증은 `asyncio.to_thread`로 실행해 이벤트 루프를 막지 않습니다 (REQ-101).

### 4.6 이메일 처리
- 저장과 조회 모두 소문자 정규화합니다. 공백은 제거합니다.
- 중복 판정은 DB UNIQUE 제약(`uk_users_email`)을 최종 기준으로 씁니다. 가입 경쟁 상태에서도 한 쪽만 성공합니다 (REQ-105).
- 다른 무결성 오류는 409로 바꾸지 않고 그대로 전파합니다.

### 4.7 세션 검증 조건
- 조회 조건은 `expires_at > UTC now`입니다. 만료 세션은 조회되지 않습니다.
- 로그아웃은 세션 행을 삭제하므로 같은 토큰은 즉시 무효화됩니다.
- 계정 삭제 시 `ON DELETE CASCADE`로 세션이 함께 삭제됩니다.

## 6. 확인된 사항과 정정

### 6.1 ADR-002 정정
- 기존 문구: "bcrypt는 72바이트 이후를 조용히 무시한다."
- 정정: "bcrypt 5.x부터는 72바이트를 초과하면 `ValueError`를 발생시키므로, Pydantic 단계의 72바이트 사전 검증이 필수다."
- 결정 내용(72바이트 제한)은 바뀌지 않았습니다. 설명만 바로잡았습니다.

### 6.2 이번 단계에서 발견한 사항
- 로그인 시도 제한(rate limit)은 구현하지 않았습니다. 명세에 요구사항이 없어 범위에서 뺐습니다. 무차별 대입을 막으려면 후속 과제로 필요합니다.
- REQ-003(사용자별 데이터 격리)은 "현재 사용자 식별"까지만 구현했습니다. 자원별 소유자 검사는 단어장 API에서 적용합니다.
