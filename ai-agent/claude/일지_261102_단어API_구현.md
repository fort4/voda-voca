## 3. 핵심 정책

### 3.1 소속 및 소유권 검증 (REQ-003, 404 일원화)
- 모든 요청은 먼저 `get_owned_wordbook`으로 단어장 소유자를 확인합니다. 이 함수는 단어장 API와 공유합니다.
- 단어 조회 조건에는 `wordbook_id = ?`를 함께 겁니다. 따라서 다음 세 경우가 모두 404입니다.
  1. 타인 소유 단어장
  2. 존재하지 않는 단어장
  3. 같은 사용자의 다른 단어장에 속한 단어 (또는 타인·존재하지 않는 단어)
- 단어장 수준 404와 단어 수준 404는 각각 같은 본문을 씁니다. 응답으로 ID 존재 여부를 알 수 없습니다.
- 테스트 `test_other_users_wordbook_is_404_for_every_word_operation`, `test_word_in_other_wordbook_of_same_user_is_404`, `test_foreign_and_missing_word_ids_give_identical_404`가 이를 확인합니다.

### 3.2 표제어 접두사 검색 (REQ-009, REQ-113)
- 쿼리 형태: `WHERE wordbook_id = ? AND term LIKE ? ESCAPE '\\' ORDER BY term, id LIMIT ? OFFSET ?`
- **이스케이프**: `escape_like()`가 `\`, `%`, `_`를 리터럴로 바꿉니다. 이스케이프 문자 자신(`\`)을 먼저 바꿔야 뒤에 붙는 이스케이프가 꼬이지 않습니다.
- **바인딩**: 검색어 값은 바인딩 파라미터로 넘깁니다. 문자열을 SQL에 이어 붙이지 않습니다 (REQ-113).
- **정규화**: 검색어는 앞뒤 공백을 제거하고 최대 100자로 제한합니다. 공백만 있거나 비어 있으면 전체 목록을 반환합니다.
- **대소문자·악센트**: 콜레이션 `utf8mb4_0900_ai_ci`가 처리합니다. `AP`로 `apple`이 나오고, `cafe`로 `café`가 나옵니다.
- 테스트: 접두사 경계(`ap` → `apple`, `apricot`만, `pineapple` 제외), 대소문자 무시, 악센트 무시, 와일드카드 리터럴 처리, 빈 검색어, 검색 결과의 `total`, 100자 초과 422.

### 3.3 표제어 중복과 동시성 제어 (REQ-105)
- 생성과 표제어 수정 모두 DB UNIQUE `uk_words_wordbook_term(wordbook_id, term)` 위반을 최종 기준으로 삼습니다.
- 애플리케이션에서 먼저 조회하지 않으므로 동시 요청에도 한쪽만 성공합니다. 실패한 쪽은 `IntegrityError`를 잡아 409로 바꿉니다.
- 위반이 다른 제약 때문이면 바꾸지 않고 그대로 전파합니다.
- 콜레이션 때문에 `Apple`과 `apple`, `café`와 `cafe`는 같은 표제어입니다. 이 동작은 설계 D2에서 확정했고, 테스트가 확인합니다.
- 다른 단어장에서는 같은 표제어를 쓸 수 있습니다.

### 3.4 부분 수정과 CASCADE
- `term`과 `meaning`은 null로 바꿀 수 없고, `example`은 null로 지울 수 있습니다.
- 값이 같으면 UPDATE가 나가지 않으므로 `updated_at`이 바뀌지 않습니다.
- 단어 삭제는 DB의 `ON DELETE CASCADE`로 북마크와 학습 이력을 함께 지웁니다. 테스트가 세 테이블의 행이 실제로 사라졌는지 확인합니다.

## 4. EXPLAIN 분석 결과

검색 쿼리가 `uk_words_wordbook_term` 인덱스를 쓰는지 확인하는 테스트를 작성했습니다. 초기 구현에서는 두 가지 문제를 발견하고 바로잡았습니다.

### 4.1 테스트 방식 수정
- 처음에는 `literal_binds`로 SQL을 렌더링해 EXPLAIN했습니다. 이때 `%`가 `%%`로 이중 이스케이프되어, 실제 실행 쿼리와 다른 SQL이 되었습니다.
- 수정: 실제 실행과 같은 **바인딩 파라미터**로 EXPLAIN합니다.

### 4.2 넓은 접두사에서의 CBO 판단
- 300행 중 33%(100행)가 걸리는 접두사 `word00`에서 옵티마이저는 **전체 테이블 스캔 + filesort**를 선택했습니다.
  - `type: ALL`, `key: NULL`, `Extra: Using where; Using filesort`
- 이유: 비용 기반 옵티마이저(CBO)가 인덱스로 33%를 읽고 정렬하는 비용보다, 작은 테이블을 한 번 훑고 정렬하는 비용이 낮다고 추정한 것입니다. 행이 많아지면 판단이 바뀔 수 있습니다.
- 이 결과는 정상적인 옵티마이저 동작입니다. 쿼리 자체의 결함이 아닙니다.

### 4.3 선택적인 접두사에서의 인덱스 레인지 스캔
- 1행만 걸리는 접두사 `word0001`에서는 `uk_words_wordbook_term`을 레인지 스캔하고, filesort가 없었습니다.
  - `key: uk_words_wordbook_term`, `type: range`, `rows: 1`, `Extra: Using index condition`
- 테스트 `test_selective_prefix_search_uses_unique_index`가 이 결과를 단언합니다.

### 4.4 해석 시 주의
- "인덱스 순서대로 읽어 filesort가 없다"는 선택적인 접두사에서만 보장됩니다. 넓은 접두사에서는 옵티마이저가 선택하며, 단어 수가 크게 늘면 실행 계획을 다시 확인해야 합니다.
- REQ-103의 성능 목표(p95 300ms)는 현재 데이터 규모에서는 문제가 없지만, 대량 데이터 검증은 아직 하지 않았습니다.
