## 2. 아이콘 미표기 버그 — 원인과 수정

### 2.1 근본 원인
- 이전 단계에서 Lucide 로더를 `lucide@0.263.1`로 고정했습니다. 그런데 **이 버전은 npm 레지스트리에 존재하지 않습니다.** 그래서 CDN에서 404가 나고, 전역 객체 `window.lucide`가 정의되지 않았습니다. 정적 아이콘이든 동적 아이콘이든 한 개도 그려지지 않았습니다.
- 동적 렌더링 문제는 그 다음 층의 문제였습니다. 라우터가 화면을 그린 뒤 아이콘을 변환하는 훅이 없었고, 모달은 MutationObserver에만 기대고 있었습니다.

### 2.2 수정
- **버전 교정**: `lucide@0.460.0`(2024-11, 요구 기준인 2주 이상 경과)로 바꿨습니다. 실제 번들을 받아 Node에서 불러와 `icons` 키를 확인했습니다 (1,737개).
- **아이콘 이름 검증**: 앱이 쓰는 아이콘 22종을 실제 빌드와 대조해 모두 존재함을 확인했습니다. 이 과정에서 Lucide 0.460에서 이름이 바뀐 것은 없었습니다.
- **공통 헬퍼 `refreshIcons()`** (`core/dom.js`): Lucide가 없으면 `false`를 돌려주고 예외를 던지지 않습니다. 있으면 `createIcons()`를 호출합니다.
- **라우터 훅**: `createRouter`에 `afterRender`를 추가했습니다. 화면이 그려질 때마다 `refreshIcons`가 호출됩니다 (`app.js`에서 연결).
- **모달 보강**: 일괄 등록 모달은 `didOpen`에서 호출합니다. 그 밖의 SweetAlert2 모달은 MutationObserver가 새 노드의 `i[data-lucide]`를 감지해 처리합니다. 변환으로 생긴 SVG가 다시 감지를 일으키지 않도록 검사 대상을 자리표시자로만 한정했습니다.

### 2.3 회귀 테스트
- `tests/dom.test.js` 3건: Lucide가 없을 때 안전한지, 있으면 호출되는지, `createIcons`가 없는 객체를 무시하는지 확인합니다. 이 테스트는 "로더 URL 404" 같은 CDN 문제를 잡지는 못합니다. 그 검사는 위의 실제 빌드 대조로 수행했습니다.

## 3. 퀴즈: 문항별 즉시 정오와 해설

### 3.1 백엔드 계약 변경
- `POST /api/study/quiz/sessions` 응답의 문항에 **`correct_index`(정답 선지 번호, 0~3)** 와 **`example`(해설용 예문, 없으면 null)** 을 추가했습니다.
- 세션 생성 시 문항 JSON에 `example`을 함께 저장합니다. 예전에 만든 세션에는 이 키가 없으므로 응답은 `null`입니다.
- 채점과 기록 로직(`POST /submit`)은 그대로입니다.

**트레이드오프 (명시적으로 기록)**: 이전 설계는 정답 인덱스를 제출 전까지 숨겼습니다. 이번 요구로 정답이 출제 응답에 함께 나갑니다. 따라서 정답을 보고 같은 답을 골라 제출하면 학습 기록에 정답이 쌓일 수 있습니다. 자기 학습용 앱이라는 전제에서 이 위험은 수용했지만, 기록 신뢰도가 중요해지면 설계를 다시 봐야 합니다.

### 3.2 프론트엔드 흐름 (`core/quiz-flow.js`, `views/quiz.js`)
- 보기를 누르면 **즉시 판정**합니다. 정답은 초록, 내가 고른 틀린 답은 빨강으로 표시합니다. 판정 뒤에는 정답 선지에 체크 아이콘이 붙습니다.
- 판정 직후 하단에 **정답 뜻과 예문 해설 카드**가 나옵니다. 예문이 없으면 "해설 예문이 없습니다"를 씁니다.
- 해설 카드의 **[다음 문항]** 버튼으로 넘어갑니다. 마지막 문항에서는 **[최종 결과 보기]** 버튼이 나오고, 이때 제출 API를 호출해 기록을 남긴 뒤 기존 결과 화면(채점 요약, 오답 노트, 전체 문항 비교)으로 바뀝니다.
- 한 문항은 한 번 답하면 잠깁니다. 이전 문항으로 돌아가 볼 수는 있지만 답은 바뀌지 않습니다.
- 타이머(세션 30분 카운트다운)와 결과 캐싱(새로고침 복구)은 이전 단계와 같습니다.

### 3.3 상태 머신 분리
- `core/quiz-flow.js`는 화면 없이 동작합니다: 판정, 잠금, 해설 기록, 이동 규칙, 제출 조건, 제출 본문, 정답 개수, 진행률.
- 테스트 11건이 이 규칙을 고정합니다. 예: 답하기 전에는 다음으로 갈 수 없음, 잠긴 문항은 바뀌지 않음, 잘못된 번호는 기록되지 않음, 빈 세션은 제출 불가.

## 4. 기본 단어장 3종 자동 제공

### 4.1 시드 데이터 (`src/backend/data/seeds/`)
| 파일 | 단어장 이름 | 개수 |
| :--- | :--- | :-: |
| `beginner_200.json` | 초급 필수 영단어 200 | 200 |
| `intermediate_200.json` | 중급 핵심 영단어 200 | 200 |
| `advanced_200.json` | 고급 심화 영단어 200 | 200 |

- 각 항목은 `{term, meaning, example}`입니다.
- 검증 (자동 테스트): 단어장당 정확히 200개, 같은 단어장 안에서 대소문자 무시 중복 없음, 필드 비어 있음 없음, 표제어·뜻·예문 글자 수 제한 이내, **예문에 표제어가 들어 있음** (해설 품질의 최소 기준).
- 작성 과정: 초급은 일상 단어 위주, 중급은 B1 수준 학술·생활 어휘, 고급은 C1 수준 어휘로 작성했습니다. 목록을 넉넉히 만든 뒤 조건(단일 단어, 예문에 표제어 포함, 중복 없음)을 기계적으로 맞추고 200개로 잘라냈습니다.
- **사람 검수 필요**: 뜻과 예문은 작성자가 직접 쓴 것이라, 특히 고급 단어의 뉘앙스 뜻과 중급 일부 예문은 원어민 또는 교사의 검수를 받는 것이 바람직합니다.

### 4.2 가입 시 생성 (`services/seed.py`, `services/auth.py`)
- `default_wordbooks()`가 세 파일을 한 번 읽어 캐시합니다.
- `signup()`은 한 트랜잭션에서 다음을 수행합니다.
  1. 사용자 행을 flush해 `user.id`를 얻습니다.
  2. 단어장 3개를 그 `user_id`로 만들고, 각각 flush해 `wordbook_id`를 얻습니다.
  3. 단어 600건을 Core `executemany`로 한꺼번에 넣습니다.
  4. 한 번만 커밋합니다.
- 닉네임 중복이면 커밋이 실패하고 롤백됩니다. 사용자도 단어장도 단어도 남지 않습니다 (테스트로 확인).
- 소유권과 격리는 기존 구조를 그대로 씁니다. 기본 단어장은 `user_id`를 가지며, 다른 사용자는 404를 받습니다 (테스트로 확인).

### 4.3 기존 테스트 조정
- 가입하면 단어장이 3개 생기므로, 단어장 목록 개수에 의존하던 테스트 6건의 기대값을 바꿨습니다. 헬퍼에 `DEFAULT_WORDBOOK_COUNT`와 `DEFAULT_WORDBOOK_NAMES` 상수를 두어 기대값을 명시했습니다.
- 퀴즈 오답 보기 테스트는 의미가 바뀌었습니다. 예전에는 "뜻이 모두 같으면 출제 불가"였지만, 이제 사용자 전체 단어(기본 단어장 포함)에서 오답을 채우므로 출제가 성공합니다. 테스트를 "전체 풀에서 오답을 채운다"로 바꿨습니다.

### 4.4 성능
- 가입마다 단어 600건이 들어가므로, 처음에는 ORM 객체 600개를 만들어 전체 테스트 시간이 17초에서 59초로 늘었습니다.
- Core `executemany`로 바꿔 20초 안팎으로 돌아왔습니다. 트랜잭션 의미는 같습니다.
