## 2. REQ-121 구현 상세

### 2.1 집계 방식: 이중 키 슬라이딩 윈도우
- 로그인 실패 한 건마다 두 개의 키에 같은 시각을 기록합니다.
  - `ip:{client_ip}`: 요청의 `request.client.host`
  - `acct:{email}`: 요청 이메일을 `strip().lower()`로 정규화한 값
- 키마다 실패 시각을 담은 `deque`를 둡니다. 판정 때 윈도우(60초) 밖의 기록을 앞에서부터 버립니다.
- 두 키 중 하나라도 실패 기록이 5건 이상이면 차단합니다. 이것이 "IP 또는 계정 중 하나라도 한도에 도달하면 차단" 규칙입니다.

### 2.2 차단 판정 순서
1. 요청마다 두 키의 윈도우를 정리하고, 한도 도달 여부를 확인합니다.
2. 차단이면 DB 조회 없이 즉시 429를 반환합니다. 비밀번호가 맞더라도 차단됩니다.
3. 허용이면 인증을 수행합니다.
4. 실패하면 두 키에 실패를 기록하고 401을 반환합니다.
5. 성공하면 **계정 키만** 리셋합니다. IP 키는 그대로 둡니다. 한 IP가 정상 계정으로 성공한 기록이 다른 계정의 공격 집계를 지우면 안 되기 때문입니다.

### 2.3 설계 판단
- **차단된 요청은 실패로 세지 않습니다.** 공격자가 차단 상태에서 계속 두드려도 차단 기간이 늘어나지 않습니다. 차단은 가장 오래된 실패로부터 60초 뒤에 풉니다.
- **"5회 초과"의 해석**: 5회 실패까지는 401이고, 여섯 번째 시도부터 429입니다. 명세 문구 "1분 내 5회 실패 시 차단"을 그대로 따른 것입니다.
- **시계 주입**: `LoginRateLimiter`는 `clock` 인자를 받습니다. 기본값은 `time.monotonic`입니다. 테스트는 가짜 시계를 넣어 윈도우 경계를 정확히 검증합니다.
- **X-Forwarded-For 미신뢰**: 역방향 프록시 뒤에서는 모든 요청이 프록시 IP로 집계됩니다. 프록시 설정이 생기면 신뢰할 헤더를 명시적으로 정해야 합니다. 지금은 보안상 기본값으로 무시합니다.

## 3. 429 응답 규격과 Retry-After 산출

### 3.1 응답
```
HTTP/1.1 429 Too Many Requests
Retry-After: 37
Content-Type: application/json

{"detail": "로그인 시도가 너무 많습니다. 잠시 후 다시 시도해 주세요."}
```

### 3.2 Retry-After 산출 로직
- 차단된 키들 각각에 대해 `남은 시간 = 가장 오래된 실패 시각 + 60초 - 현재 시각`을 계산합니다.
- 여러 키가 차단되었다면 그중 **가장 긴 대기 시간**을 씁니다. 그래야 재시도 시점에 실제로 풀려 있습니다.
- 값은 올림하고 최소 1로 맞춥니다. 소수 초나 0초를 보내지 않으므로 클라이언트가 파싱하기 쉽습니다.
- 테스트 `test_retry_after_counts_down_from_the_oldest_failure`가 카운트다운 값을 확인합니다. 통합 테스트 `test_429_carries_positive_integer_retry_after`는 헤더가 1 이상의 정수인지 확인합니다.

## 4. 테스트 결과

### 4.1 단위 테스트 (`test_rate_limit_units.py`, 11건)
DB 없이 가짜 시계로 `LoginRateLimiter`만 검증합니다.
- 4회까지 허용, 5회째 차단
- Retry-After 카운트다운이 가장 오래된 실패를 기준으로 줄어듦
- 정확히 60초가 지나면 차단 해제 (59초에서는 차단 유지)
- 오래된 실패가 한 건씩 윈도우에서 빠짐
- 키 독립성, 두 키 중 하나만 차단돼도 요청 차단
- `reset`은 지정한 키만 지움, `clear`는 전부 지움
- 없는 키에 `reset`해도 예외가 없음
- 윈도우가 완전히 빠진 뒤 새로 실패하면 1건부터 다시 셈

### 4.2 통합 테스트 (`test_login_rate_limit_api.py`, 8건)
실제 로그인 라우트와 MySQL을 사용합니다. IP가 다른 클라이언트 3개(`10.0.0.1~3`)를 만들어 IP 키와 계정 키를 따로 검증합니다.
- 여섯 번째 시도는 올바른 비밀번호여도 429
- Retry-After가 1 이상 60 이하의 정수
- 계정 키: IP를 바꿔도 같은 계정은 차단
- IP 키: 한 IP가 여러 계정을 찔러 차단되면, 그 IP는 다른 계정도 차단. 다른 IP는 정상
- 성공 로그인이 계정 카운터를 리셋 (리셋 후 4회씩 실패해도 차단되지 않음)
- 차단 요청은 집계되지 않음, 60초 경과 후 올바른 비밀번호로 로그인 성공 (가짜 시계 사용)
- 형식이 잘못된 이메일도 IP 키로 집계되며, 실패 응답은 401 유지
- 로그인 차단이 가입과 `/me`에는 영향 없음

### 4.3 전역 상태 격리: autouse 픽스처
- `login_rate_limiter`는 프로세스 전역 객체입니다. 테스트들이 같은 IP(기본 `127.0.0.1`)를 쓰므로, 격리하지 않으면 앞선 테스트의 실패가 뒤 테스트에 넘어갑니다.
- 해결: `src/backend/tests/conftest.py`에 `_reset_login_rate_limiter` autouse 픽스처를 두어 **각 테스트 전후로 `clear()`**를 호출합니다.
- 픽스처가 있어야 할 이유가 실제로 있었습니다. 통합 테스트는 한 테스트 안에서 실패를 5회 이상 만들기 때문에, 격리 없이는 테스트 순서에 따라 결과가 달라집니다.

## 5. 단일 프로세스 특성과 다중 워커 확장

### 5.1 현재 동작의 한계
- 집계 상태는 **프로세스 메모리**에 있습니다. 워커가 하나면 정확하게 동작합니다.
- 워커를 여러 개 띄우면(예: `uvicorn --workers 4` 또는 컨테이너 복제) 각 워커가 따로 집계합니다. 공격자가 요청을 여러 워커에 나눠 보내면 한도가 실질적으로 워커 수만큼 늘어납니다.
- 재시작하면 집계가 모두 사라집니다. 차단 중이던 공격자도 재시작 직후에는 다시 시도할 수 있습니다.
- 키는 접근할 때만 정리합니다. 한 번 실패하고 다시 오지 않은 키의 기록은 재시작 전까지 남습니다. 규모가 작아 현재는 문제가 되지 않습니다.

### 5.2 Redis 전환 필요 조건
- 다음 중 하나라도 생기면 공유 저장소(예: Redis)로 옮겨야 합니다.
  - 다중 워커 또는 다중 인스턴스 배포
  - 재시작 후에도 차단 상태를 유지해야 하는 요구
- 전환 방식: 같은 키 구조를 Redis `INCR`과 `EXPIRE`로 구현하면 됩니다. 인터페이스(`retry_after`, `record_failure`, `reset`)를 그대로 두면 라우터는 바뀌지 않습니다.
- 현재 단계에서 Redis를 도입하지 않은 이유: 요구사항 REQ-121에 "외부 저장소 없이 메모리에서 관리한다"로 적었고, 단일 프로세스 배포가 1차 범위이기 때문입니다.
