## 3. 핵심 정책

### 3.1 멱등 등록과 중복 제어 (REQ-017, REQ-105)
- PUT은 여러 번 호출해도 결과가 같습니다. 이미 등록된 상태에서 호출하면 UNIQUE `uk_bookmarks_user_word` 위반을 잡아 성공(204)으로 처리합니다.
- 애플리케이션에서 먼저 조회하지 않습니다. 동시 요청이 와도 DB가 행을 하나만 허용하고, 나머지는 같은 성공 응답을 받습니다.
- 테스트: `test_put_is_idempotent`, `test_concurrent_puts_create_exactly_one_row`

### 3.2 소유권과 404 일원화 (REQ-003)
- 등록 전에 `_ensure_owned_word`가 요청 사용자 소유 단어장의 단어인지 확인합니다.
- 타인 단어와 존재하지 않는 단어는 같은 404 본문을 씁니다. 응답으로 단어 ID 존재 여부를 알 수 없습니다.
- 해제는 요청 사용자의 행만 지웁니다. 다른 사용자의 북마크를 지울 수 없습니다.
- 테스트: `test_put_on_other_users_word_is_404_same_as_missing`, `test_intruder_delete_does_not_touch_owners_bookmark`

### 3.3 단어 목록의 `bookmarked` 필드 (LEFT JOIN)
- 단어 목록 쿼리는 `bookmarks`를 `LEFT OUTER JOIN`합니다. 조인 조건은 `Bookmark.word_id == Word.id AND Bookmark.user_id == 요청자`입니다.
- 북마크 행이 있으면 `bookmarked = true`, 없으면 `false`가 됩니다. 조인 조건에 사용자를 넣어, 다른 사용자의 북마크가 섞이지 않습니다.
- 같은 로직을 단어 상세, 생성, 수정 응답에도 적용합니다 (`is_bookmarked`).
- 테스트: `test_word_list_bookmarked_flag_matches_bookmarks`, `test_bookmarked_flag_is_consistent_with_prefix_search`, `test_bookmarked_flag_on_get_patch_and_create`

### 3.4 CASCADE 삭제 검증
- 단어 삭제 시 `bookmarks`의 행이 DB의 `ON DELETE CASCADE`로 함께 삭제됩니다.
- 단어장 삭제 시 그 안 단어들의 북마크도 함께 삭제됩니다.
- 테스트: `test_deleting_word_removes_its_bookmark`, `test_deleting_wordbook_removes_bookmarks_of_its_words`

### 3.5 목록 페이징 및 정렬
- `page >= 1`, `1 <= size <= 100`(기본 20)입니다. 범위를 벗어나면 422입니다.
- 테스트: `test_list_is_newest_first_and_paginated`, `test_list_rejects_out_of_range_paging`, `test_list_shows_only_own_bookmarks`

## 4. DB 세션 예외 롤백 보장 (선행 아키텍처 보완)

### 4.1 문제 인식과 대상 위치
- 요청 중 예외가 나면 미완료 트랜잭션을 명시적으로 되돌리는 코드가 없었습니다. 세션을 닫으면 롤백되긴 하지만, 그 순서가 코드에 드러나 있지 않았습니다.
- 대상 함수는 요청 설계서상 `core/deps.py`로 언급되었으나, 실제 위치는 **`src/backend/db/session.py`의 `get_db_session()`** 입니다. 수정은 실제 위치에서 했습니다.

### 4.2 변경 내용
```python
session = get_session_factory()()
try:
    yield session
except Exception:
    await session.rollback()   # 1) 예외 시 명시적으로 롤백을 await
    raise
finally:
    await session.close()      # 2) 예외 여부와 무관하게 세션 닫기 (커넥션 반납)
```

- 롤백을 `finally`가 아니라 `except`에 둔 이유: 정상 종료 시에는 커밋되지 않은 변경을 되돌릴 이유가 없고, 롤백은 예외 경로에서만 의미가 있습니다.
- `Exception`만 잡은 이유: `GeneratorExit`와 `CancelledError`(BaseException)는 정리 과정에서 await를 하지 않도록 두었습니다. 이 경우에도 `finally`의 `close()`는 실행됩니다.
- `rollback()`이 실패하면 그 예외가 전파되고 원래 예외는 `__context__`에 남습니다. `finally`의 `close()`는 여전히 호출됩니다.

### 4.3 검증 테스트 (`src/backend/tests/test_db_session.py`, 4건)
| 테스트 | 검증 내용 |
| :--- | :--- |
| `test_normal_exit_closes_without_rollback` | 정상 종료 시 rollback 없이 close만 호출 |
| `test_exception_rolls_back_then_closes_and_propagates` | 예외 시 rollback과 close가 호출되고, 예외가 그대로 전파 |
| `test_rollback_happens_before_close` | 호출 순서가 rollback → close |
| `test_close_still_runs_when_rollback_fails` | rollback이 실패해도 close는 호출 |
