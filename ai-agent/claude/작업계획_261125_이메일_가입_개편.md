# 작업계획: 이메일 기반 가입·로그인 개편 (이슈 #27, REQ-158)

> **⚠ 개정 (2026-11-26): 이메일·Google OAuth 를 하지 않기로 결정했다.** 아래 §1~§8 은 이메일 도입안의 기록이며 폐기됐다.
> 최종 범위는 **닉네임 + 비밀번호 유지, 비밀번호 확인, 닉네임 "사용 가능 확인" 버튼**이다 (이슈 #27 본문, #28 닫음).
> `users.email`·마이그레이션 0003·기존 계정 삭제·`check-email`·이메일 로그인은 구현했다가 걷어냈다. 스키마 변경은 없다.
> 최종 API: `POST /api/auth/signup {nickname, password, password_confirm}`, `GET /api/auth/check-nickname?nickname=`,
> 로그인 `{nickname, password}` 불변. 409 는 `X-Error-Code: NICKNAME_TAKEN`. 확인 API 는 IP 당 1분 30회.


- 작성: 2026-11-25 / 상태: **초안 (사용자 승인 대기)**
- 관련: 이슈 #27(본 작업), #28(Google OAuth, 후속), REQ-001·002·121·156④ 개정, VOCA-FR 회원 기능

## 1. 확정 결정 (사용자, 2026-11-25)

| 항목 | 결정 |
| :--- | :--- |
| 식별자 | 이메일 (고유, 대소문자 무시). 로그인도 이메일 + 비밀번호 |
| 닉네임 | 고유 유지 (기존 `uk_users_nickname`) |
| 비밀번호 | 안전 비밀번호 정규식 **배제**. 기존 규칙(8자 이상, 72바이트 이하) 유지 |
| 비밀번호 확인 | 가입 시 2차 입력. 일치하면 "비밀번호가 동일합니다" 표시 |
| 중복 확인 | 이메일·닉네임 각각 "사용 가능 확인" 버튼. 누르면 중복 여부 안내 |
| 기존 계정 | 모두 삭제 후 재가입 (이행 로직 없음) |
| 이메일 수집 필요성 | 미결정 (#28 OAuth 결정에 달림). 지금 설계는 로그인 식별자로 쓰므로 OAuth 와 무관하게 유효 |

## 2. 요구사항 (명세 개정 초안)

**REQ-158 (신설, M) 이메일 기반 가입·로그인**
1. 가입 입력: 이메일, 닉네임, 비밀번호, 비밀번호 확인. 서버 `POST /api/auth/signup` 가 넷을 모두 받는다.
2. 이메일: 앞뒤 공백 제거 후 소문자로 정규화해 저장. 최대 254자. 형식 `로컬@도메인.최상위` (공백·`@` 중복 불가). 대소문자와 무관하게 유일.
3. 닉네임: 기존과 같다 (공백 제거 후 2~30자, 대소문자 무관 유일).
4. 비밀번호 확인: 서버가 `password` 와 `password_confirm` 이 다르면 422. 클라이언트는 입력 즉시 일치 여부를 표시한다.
5. 중복 확인 API (로그인 불필요):
   - `GET /api/auth/check-email?email=` → `{"available": true|false}`
   - `GET /api/auth/check-nickname?nickname=` → `{"available": true|false}`
   - 형식이 틀리면 422 (사용 가능/불가로 답하지 않는다). 계정 존재 여부가 드러나므로 **IP 기준 1분 30회**로 제한하고 초과 시 429 + `Retry-After`.
6. 가입 제출 시 서버가 중복을 다시 검사한다. 이메일 중복 409 "이미 가입된 이메일입니다.", 닉네임 중복 409 "이미 사용 중인 닉네임입니다." (어느 필드인지 `field` 로 구분).
7. 로그인: `POST /api/auth/login` 의 입력이 `{email, password}`. 실패 메시지는 "이메일 또는 비밀번호가 올바르지 않습니다." (어느 쪽이 틀렸는지 노출하지 않는다, REQ-002).
8. 응답 `UserOut` 에 `email` 을 추가한다 (본인 정보).
9. REQ-121(무차별 대입 방어)의 계정 키는 **정규화한 이메일**로 바꾼다.
10. REQ-156 ④ 의 "소셜 로그인은 하지 않는다" 는 #28 결정 전까지 유지한다.

**화면 규칙** (모바일 우선)
- 가입: 이메일 [확인] / 닉네임 [확인] / 비밀번호 / 비밀번호 확인. 확인 버튼은 44px 이상, 결과는 `aria-live="polite"` 로 알린다.
- 확인 후 값을 고치면 확인 결과를 무효로 되돌린다. **가입하기는 두 값이 현재 값 기준으로 "사용 가능" 확인된 뒤에만 활성화**한다 (서버는 확인 여부와 무관하게 항상 재검사).
- 비밀번호 확인란: 일치 "비밀번호가 동일합니다"(초록), 불일치 "비밀번호가 일치하지 않습니다"(빨강), 비어 있으면 안내 없음.
- 로그인: 이메일 + 비밀번호. 닉네임은 계정 메뉴·인사말에 표시용으로만 쓴다.

## 3. 설계

### 3.1 데이터 (`users`, 마이그레이션 0003)
- `email` String(254, NOCASE) NOT NULL, `UniqueConstraint("email", name="uk_users_email")`, `CheckConstraint("length(trim(email)) > 0", ...)`.
- **기존 계정 삭제**: 마이그레이션 `upgrade()` 가 `DELETE FROM users` 를 먼저 실행한다 (외래키 CASCADE 로 세션·북마크·이력·진행도·퀴즈 세션도 삭제). 그래야 NOT NULL 컬럼을 추가할 수 있고, 어느 환경에서 적용해도 결과가 같다.
- SQLite 는 제약 추가에 `batch_alter_table` 이 필요하다 (0002 와 같은 방식). `downgrade()` 는 컬럼·제약만 제거한다 (삭제된 계정은 복구 불가).
- ⚠ 서버 시작 시 `docker-entrypoint.sh` 가 마이그레이션을 자동 적용하므로, **실제 DB(로컬 `/data` 볼륨)에는 사용자 승인과 백업 후에만 적용**한다. 테스트는 임시 SQLite 라 영향이 없다.

## 7. 위험과 확인 요청
- **데이터 삭제**: 0003 이 사용자 데이터를 지운다. 로컬 DB 적용 전 백업과 승인이 필요하다.
- **확인 API 로 계정 존재 여부 노출**: 레이트 리밋으로 완화. 완전한 열거 방지는 아니다 (가입 화면의 일반적인 절충).
- **이메일 미검증**: 소유 확인 메일을 보내지 않는다 (서버 인터넷 차단, VOCA-SUB-036). 형식만 검증하므로 타인의 이메일로 가입할 수 있다. #28 OAuth 에서는 Google 이 검증한 이메일만 연결해야 한다.
- 단계 5 의 푸시는 1차 제출(11-30 23:59) 전에 끝낸다. 이후 C단계(단어 관리)는 일정이 빠듯하다.
