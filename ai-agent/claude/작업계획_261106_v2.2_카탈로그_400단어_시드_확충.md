### 2.1 사양과 현행 코드의 차이 (확인 필요)

| 사양 표기 | 현행 코드 | 이 계획의 처리 |
| :--- | :--- | :--- |
| `word` | `term` | **`term` 유지.** 키 이름을 바꾸면 기존 3개 파일 600건과 로더·테스트를 모두 고쳐야 하고 얻는 것이 없다 |

| `part_of_speech` | JSON 키 없음, DB 컬럼은 `pos` | JSON 키는 **`pos`** 로 신설해 DB 컬럼과 이름을 맞춘다 (결정 1) |

## 3. 설계

### 3.1 시드 메타 (`vocabularies.json` 에 2건 추가)

| slug | title (안) | category | level | sort_order | description (안) |
| :--- | :--- | :--- | :---: | :---: | :--- |
| `toeic-core-200` | TOEIC 빈출 영단어 200 | `EXAM` | 결정 2 | 4 | 시험 지문과 문제에 자주 나오는 비즈니스·일상 어휘 |
| `business-practical-200` | 실무 비즈니스 영단어 200 | `BUSINESS` | 결정 2 | 5 | 회의·이메일·협상 등 직장에서 바로 쓰는 어휘 |

기존 3건의 메타(`sort_order` 1~3 포함)는 **한 글자도 바꾸지 않는다.**

### 3.2 단어 항목 규격 (신규 2개 파일)

```json
{ "term": "invoice", "phonetic": "ˈɪnvɔɪs", "pos": "noun",
  "meaning": "청구서, 송장",
  "example": "Please send the invoice by Friday.",
  "example_meaning": "금요일까지 청구서를 보내 주세요." }
```

- `phonetic`: v2.2 규격 그대로 — 슬래시·대괄호 없는 순수 미국식 IPA, 로더의 문자 검증 통과. **음절 규칙**은 기존 관문 테스트와 같다: 단음절에는 강세 표시 없음, 1차 강세(ˈ)는 단어당 최대 1개.
- `meaning`: 200자 이하, `example`/`example_meaning`: 500자 이하 (기존 한도).
- **예문 표제어 일치**: 예문 안에 표제어(또는 그 활용형)가 들어 있어야 한다. 규칙은 §4.1 ⑤.

### 3.3 로더 변경 (`system_seed.py`, 최소)

1. `SeedWordData.pos: str | None = None` 추가, `_parse_words` 가 `item.get("pos")` 를 읽는다 (`_text`, `POS_MAX = 20`, 선택).
2. **해시 불변 설계 (핵심)**: 단어 항목 리스트의 **끝에 `pos` 를 `None` 이 아닐 때만** 덧붙인다.
   - `pos` 가 없는 기존 600단어 → 리스트가 지금과 **바이트 단위로 같다** → 세 단어장 `content_hash` 불변 → 시작 시 `unchanged`.
   - 키가 없는 것과 명시적 null 은 같은 내용 (phonetic 과 같은 원칙).
3. 갱신 비교 튜플·INSERT 딕셔너리에 `pos` 추가 (값 변경→UPDATE, 삭제→NULL).
4. 모델 주석의 "pos 미사용"을 "pos 사용(v2.2, 신규 단어장에 한함)"으로 정정. 스키마·마이그레이션 변경 **없음**.

> 이 변경은 신규 2개 단어장만 `created` 로 만들고 기존 3개는 건드리지 않는다. 사양의 "기존 600단어 해시 불변"을 테스트로 고정한다 (§4.2).

### 3.4 프론트엔드 (`explore-model.js`)

- `CATEGORY_LABELS` 에 `EXAM: "시험"`, `BUSINESS: "비즈니스"` 추가. 없으면 칩과 카드 배지에 `EXAM`/`BUSINESS` 가 그대로 노출된다.
- `categoryOptions` 는 "카탈로그에 실제 있는 카테고리를 처음 나온 순서로" 만들므로 `sort_order` 순서 그대로 `전체·초등·중고등·수능·시험·비즈니스` 가 된다. 로직 변경 없음.
- 점검 항목: ① 칩 6개가 360px 에서 가로 스크롤로 정상 동작하는지(수동) ② 카드 5장 레이아웃 ③ 다크 모드(색 클래스를 새로 쓰지 않으므로 `dark-theme.test.js` 영향 없음).

## 6. 개발 DB 영향과 안전장치

- `test_real_seed_…` 와 **앱 시작(lifespan) 시드**가 개발 DB 에 신규 2개 단어장 + 단어 400행을 **INSERT** 한다. 기존 행은 `unchanged`(해시 동일)라 UPDATE 도 없다. CLAUDE.md §6 상 상태 변경 DB 작업이므로 **단계 5 직전에 계획을 보고하고 승인**을 받는다.
- 적재 전 `ai-agent/backups/`(gitignore) 에 mysqldump 를 받는다. 실행 전후 `SELECT COUNT(*) FROM system_words` 600 → 1,000, `system_vocabularies` 3 → 5, 기존 3개 단어장의 `id`·`content_hash` 동일을 확인해 보고한다.
- 롤백: 신규 슬러그 2건 삭제(`ON DELETE CASCADE` 로 단어 동반 삭제). 기존 사용자 진행 데이터(`user_word_progress`)는 신규 단어를 참조하지 않으므로 영향 없음.
- 적재 후 기존 사용자의 활성 단어장·진행률은 그대로이고, 신규 단어장은 `0 / 200` 으로 보인다.

| 단어 선정 | 400개를 직접 선별한다. **ETS 등 상용 단어 목록·교재를 복제하지 않고**, 일반적인 비즈니스 영어 빈도·주제(인사·재무·마케팅·계약·출장·회의·이메일 등)로 구성한다. TOEIC 은 ETS 의 상표이므로 화면·문서에는 "TOEIC 빈출"처럼 **시험 대비 어휘라는 서술적 표기**만 쓰고 공식 제휴처럼 보이지 않게 한다 (결정 4) |
| 중복 방지 | 기존 600과 겹치는 표제어 제외 (⑥). TOEIC 과 비즈니스 사이 겹침도 제외 |
| 단어 형태 | 기본은 **단일 단어**(IPA 자동 변환·검수 용이, 기존 600과 일관). 숙어·구동사는 §10 결정 5 |
| 품사 | 한 단어가 여러 품사일 때 **예문에서 쓰인 품사 하나**를 적는다 (예문·뜻·품사 일치) |
| 뜻 | 예문의 용법에 맞는 한국어 뜻 1~3개. 동형이음·다의어는 예문 기준으로 확정 |
| IPA | 이전 작업의 변환 도구(`작업계획_261106_IPA_변환.py`, CMUdict 미국식)를 **재사용**. 미수록·동형이음(예: `record`, `permit`, `present`, `object` 처럼 품사로 강세가 갈리는 단어)은 **품사에 맞춰 수기 확정**. 출처 고지는 이미 요구사항 명세 §10 에 있고, 신규 단어에도 같은 출처 |
| 검수 | **전체 400개를 `단어 / IPA / 품사 / 뜻 / 예문` 표**로 뽑아 사용자가 훑어볼 수 있게 제출 후 병합 (`검토_261106_카탈로그_400단어_검수표.md`) |
| 생성 위치 | 초안·검수표는 `ai-agent/claude/`. 시드 JSON 병합은 승인 후 |

도구가 현재 `words/*.json` 의 기존 파일 형식만 가정하므로, 재사용 시 `pos` 키 보존과 신규 파일 생성 지원을 먼저 확인한다 (단계 4 시작 시점).

## 10. 결정이 필요한 사항 (승인 시 함께 답변)

1. **품사 표기 형식**: ⓐ 영문 전체 소문자(`noun`, `verb`, `adjective`, `adverb`, `preposition`, `conjunction`) — **추천** (사전 관례, 검증 쉬움, 20자 이내) / ⓑ 약어(`n.`, `v.`) / ⓒ 한글(`명사`). 허용 집합을 관문 테스트 ④가 강제한다. 사양 키 이름 `part_of_speech` 대신 DB 컬럼과 같은 **`pos`** 를 JSON 키로 쓰는 것도 함께 확인.
2. **level (1~5)**: 사양에 없음. 추천: TOEIC = **3**, 비즈니스 = **3** (기존 고급이 3). 필터 칩의 레벨 선택에 영향.
3. **`pos` 의 노출 범위**: ⓐ 이번에는 **DB 저장만**, API·화면 미노출 (사양에 노출 요구 없음, 문서 변경 최소) — **추천** / ⓑ 단어 목록 API(`VocabularyWordOut.pos`)와 단어 시트·해설 시트에 표시. ⓑ 는 별도 이슈로 나누는 편이 안전.
4. **단어장 제목에 "TOEIC" 사용**: 추천 `TOEIC 빈출 영단어 200` (서술적 사용). 상표 우려가 크면 `시험 대비 빈출 영단어 200`.
5. **숙어·구동사 허용**: ⓐ **단일 단어만** — **추천** (IPA 자동화·강세 관문·기존 일관성) / ⓑ "실무 회화" 취지상 `follow up`, `on behalf of` 같은 표현 일부 허용. ⓑ 는 IPA 를 토큰별로 합성해야 하고 "1차 강세 ≤ 1" 규칙과 충돌하므로 별도 규칙(토큰별 허용)과 관문 완화가 필요하다. 허용한다면 비율 상한(예: 비즈니스 200 중 40개 이내)도 정해야 한다.
6. **요구사항 번호**: 신규 **REQ-145** 로 등록 / REQ-143 확장 중 택일. 추천은 REQ-143 의 "시드" 성격이 같으므로 **REQ-143 확장 + 추적 매트릭스 갱신** (번호 증가 최소화). 다만 이슈 추적이 필요하면 REQ-145.
7. **관문 ⑤ 엄격도**: 활용형 규칙 + 예외표 방식으로 갈지, 예문에 **표제어 원형이 그대로** 들어가도록 시드를 강제할지(더 단순하나 `postponed` 같은 자연스러운 활용 예문을 못 씀). 추천은 활용형 허용.
