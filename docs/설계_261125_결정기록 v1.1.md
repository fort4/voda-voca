## ADR-001. 세션 쿠키 인증 및 DB `sessions` 테이블 관리

> **v1.1 주석**: 저장소가 MySQL 에서 SQLite 로 바뀌었다(ADR-010). 아래 결정(토큰 해시 저장, 14일 절대 만료)은 그대로이며 `id` 컬럼은 `BLOB(32)` 이다.

- **상태**: Accepted (2026-11-02, 사용자 확정: 요구사항 Q1)
- **관련 요구사항**: REQ-001, REQ-002, REQ-003, REQ-112

### 배경
- 프론트엔드는 빌드 없는 Vanilla JavaScript다 (ADR-007). 토큰을 클라이언트에서 저장하고 갱신하는 코드는 복잡도가 높다.
- 토큰을 `localStorage`에 두면 XSS로 탈취될 수 있다.
- 로그아웃 시 서버에서 인증을 즉시 끊어야 한다 (REQ-002).

### 결정
1. 서버 측 세션을 쓰고, 클라이언트에는 `HttpOnly`, `SameSite=Lax` 쿠키(`voda_session`)만 둔다. `Secure` 는 HTTPS 에서 켜고(`COOKIE_SECURE`) 개발 환경에서는 끈다.
2. DB `sessions` 테이블에 저장한다. 쿠키에는 `secrets.token_urlsafe(32)` 토큰 원문을 넣고, DB 의 `id` 에는 SHA-256 다이제스트(`BINARY(32)`)만 저장한다. DB 가 노출되어도 유효한 토큰은 노출되지 않는다.
3. 수명은 로그인 후 14일 절대 만료이며 슬라이딩 연장은 하지 않는다 (`session_ttl_days`, 기본 14).
4. 로그아웃은 해당 행을 삭제한다. 계정 삭제 시 `ON DELETE CASCADE` 로 모든 세션이 지워진다.
5. 만료 정리는 조회 시 `expires_at` 조건으로만 걸러낸다. 누적 행의 배치 삭제는 후속 과제다 (Architecture Design A5).

### 대안
| 대안 | 장점 | 단점 | 판정 |
| :--- | :--- | :--- | :--- |
| JWT (Stateless) | DB 조회 없음 | 발급 후 무효화가 어렵다. 로그아웃에 블랙리스트가 필요하다. 클라이언트 토큰 관리가 필요하다 | 기각 |
| 메모리 세션 | 가장 단순하다 | 재시작 시 세션이 사라진다. 워커 간 공유가 안 된다 | 기각 |
| Redis 세션 | 빠르고 만료 관리가 쉽다 | 스택에 없는 컨테이너를 추가해야 한다. 규모에 과하다 | 보류 |
| **DB `sessions` 테이블** | 기존 DB 재사용. 재시작 후에도 유지. CASCADE 정리 | 요청마다 PK 조회 1회 추가 | **채택** |

### 결과
- 인증 요청마다 `sessions` PK 조회가 한 번 늘지만 p95 300ms 목표(REQ-102)에 영향은 작다.
- CSRF 는 `SameSite=Lax` 가 cross-site POST 의 쿠키 전송을 막는 것으로 방어하고 별도 토큰은 두지 않는다. 같은 사이트의 다른 서브도메인은 막지 못하므로 **배포 구조가 바뀌면 재검토한다** (Architecture Design A8).
- **14일 절대 만료는 사용자가 확정했다 (2026-11-19).** 전신 문서에서 "기본값이며 사용자 확인 필요"로 남아 있던 항목이다.

## ADR-002. 비밀번호 해시 알고리즘: bcrypt

- **상태**: Accepted (2026-11-02, 사용자 선택)
- **관련 요구사항**: REQ-001, REQ-110, REQ-111

### 배경
- REQ-110 은 평문 저장을 금지하고 bcrypt 또는 argon2 중 하나를 쓰도록 했다. 소규모 서비스이므로 의존성을 단순하게 유지하는 것이 중요하다.

### 결정
1. **bcrypt** 를 쓴다. 비용 계수 기본값은 12 이며 `bcrypt_rounds` 설정으로 조정한다 (테스트에서는 낮춘다).
2. bcrypt 5.x 는 72바이트를 초과하는 입력에 `ValueError` 를 던진다. 그래서 Pydantic 단계에서 **UTF-8 기준 72바이트 이하**만 허용하는 사전 검증이 필수다. 검증을 빼먹으면 초과 입력이 서비스 계층까지 와서 500 오류가 된다. `schemas/auth.py` 와 `services/password.py` 양쪽에 방어를 둔다.
3. `password_hash VARCHAR(255)` 에 결과 문자열 전체(60자)를 저장한다.

### 대안
| 대안 | 장점 | 단점 | 판정 |
| :--- | :--- | :--- | :--- |
| **bcrypt** | 오래 검증되었고 설치가 가볍다 | 메모리 소비가 작아 GPU 공격에 argon2 보다 약하다. 72바이트 제한 | **채택** |
| argon2id | 메모리 하드 함수라 현재 권장된다. 길이 제한이 없다 | 네이티브 의존성이 필요하다. 이 규모에서 이득이 제한적이다 | 보류 |
| PBKDF2 | 표준 라이브러리 | 같은 비용에서 bcrypt 보다 약하다 | 기각 |

### 결과
- 사용자 존재 여부와 무관하게 해시 비교가 항상 한 번 실행되어, 응답 시간으로 계정 존재를 추측하지 못한다 (REQ-002).
- argon2id 로 바꾸려면 로그인 시 점진적 재해시가 필요하다. 해시 접두사(`$2b$`)로 알고리즘을 구분할 수 있다.

## ADR-003. 단어 검색: 접두사 인덱스 전략, 뜻 검색 제외

- **상태**: **Superseded** — 2026-11-05 중앙 제공형 전환(ADR-004)으로 표제어 검색 API 가 폐기되었다 (Data Design D5 "폐기", §2.5).
- **원래 관련 요구사항**: REQ-009, REQ-113

### 요약 (이력 보존)
개인 단어장 시절(`wordbooks`, `words`)의 결정이다. 표제어는 `LIKE 'keyword%'` 접두사 일치로 검색해 `UNIQUE (wordbook_id, term)` 인덱스를 그대로 쓰고, 뜻 검색은 인덱스 전략상 1차에서 제외했으며 FULLTEXT ngram 은 보류했다.

### 폐기 사유와 잔존 효과
- 단어장이 읽기 전용 공용 데이터(1,000단어, 5개 단어장)가 되어 단어장 안의 표제어 검색 기능 자체가 없어졌다. 탐색 화면은 카테고리·레벨 칩과 페이지네이션으로 거른다.
- **계속 유효한 부분**: LIKE 를 쓰는 곳에서는 `%`, `_`, `\` 를 이스케이프하고 값은 바인딩 파라미터로 전달한다 (REQ-113).
- 검색 요구가 다시 생기면 새 ADR 로 FULLTEXT ngram 인덱스를 검토한다.

## ADR-004. 중앙 제공형 표준 단어장 (사용자 단어장 폐지)

- **상태**: Accepted (2026-11-05). **사후 기록**: 당시 근거는 `ai-agent/claude/작업계획_261105_중앙제공형_단어장_아키텍처_전환.md` §1 과 Data Design §6.1 D1, D3, D5, D10, D13, D18 에 있다.
- **관련 요구사항**: REQ-140~143 (v2.2 에서 REQ-144~146 으로 확장)

### 배경
- 초기 모델은 사용자가 단어장을 만들고 CSV 를 올리는 방식이라 온보딩 허들이 높았다.
- 사용자마다 같은 단어를 각자 등록해 중복되었고 오타·불완전한 예문이 정제되지 않았다.
- 대량 파싱, CSV 인코딩(UTF-8/CP949) 예외, 개별 편집·삭제 트랜잭션 같은 비핵심 관리 비용이 컸다.

### 결정
1. 서비스가 단어장과 단어를 **읽기 전용 공용 콘텐츠**로 제공한다 (`system_vocabularies`, `system_words`). 사용자는 단어를 만들거나 고치지 않는다.
2. 원본은 저장소의 JSON 시드(`src/backend/data/seeds/`)이며 서버가 시작할 때 멱등 적재한다 (`slug`, `(vocabulary_id, term)` 으로 식별, `content_hash` 변경 시에만 UPDATE).
3. 가입 시 단어장을 복제하지 않고 `users.active_vocabulary_id` 만 지정한다.
4. 사용자별로는 활성 단어장, 북마크, 학습 기록, 단어 진행도, 학습 설정만 저장한다 (콘텐츠와 학습 상태의 분리).
5. 기존 개인 단어장 데이터는 이관하지 않고 초기화했다 (D18: 개발 DB 였고 `words` id 가 `system_words` 와 대응되지 않았다).

### 대안 (사후 정리)
| 대안 | 장점 | 단점 | 판정 |
| :--- | :--- | :--- | :--- |
| 사용자 단어장 + CSV 업로드 유지 | 사용자가 원하는 단어를 넣는다 | 위 배경의 세 가지 비용이 그대로 남는다 | 기각 |
| 가입 시 기본 단어장을 사용자별로 복제 | 사용자가 자기 사본을 고칠 수 있다 | 중복 데이터, 시드 개선이 기존 사용자에게 전파되지 않는다 | 기각 (D10 이 복제하지 않기로 명시) |
| **공용 읽기 전용 카탈로그 + 사용자 진행 상태 분리** | 품질 일괄 관리, 가입 즉시 학습, 시드 개선 전파 | 사용자 맞춤 단어 추가 불가 | **채택** |

### 결과
- 시드 변경은 서버 재시작으로 운영 DB 에 반영된다. `word_id` 가 유지되므로 학습 기록은 보존된다. 시드를 잘못 고치면 바로 DB 에 들어가므로 수정 전 백업이 필요하다 (Architecture Design A3).
- 시드 검증에 실패하면 서버 시작이 막힌다 (`init_system_seeds`).
- 사용자 맞춤 단어 기능은 범위 밖이다. 요구가 생기면 새 ADR 이 필요하다.

## ADR-005. 서버 채점, 정답 비노출, 출제 스냅샷 DB 저장

- **상태**: Accepted (2026-11-05). **사후 기록**: Data Design §6.1 D6, D7, D8, D16, D17 에서 정리.
- **관련 요구사항**: REQ-012, REQ-014, REQ-016, REQ-124

### 배경
- 퀴즈·플래시카드를 한 세션에서 진행하고 문항마다 기록한다. 세션 상태를 어디에 두고 누가 채점하는지 정해야 했다.
- 진행도·통계·SRS 가 모두 채점 결과에 의존하므로 판정 기준이 한 곳에 있어야 한다.

### 결정
1. **채점은 서버**가 한다 (`record_session_answer` → `_judge`). 클라이언트는 고른 선지 번호(퀴즈) 또는 알아요/헷갈려요(플래시카드)만 보낸다.
2. **출제 응답에는 정답과 해설을 싣지 않는다.** 정답·해설은 채점 응답에서 처음 공개한다 (D16). 코드에서 퀴즈 `SessionItemOut` 은 `correct_index` 필드가 없다.
3. 세션과 문항은 **DB 테이블 `quiz_sessions`** 에 저장한다 (D6). 출제 시점의 문항을 `questions`(JSON) 스냅샷으로 저장하고 답은 `answers` 에 문항별로 쌓는다.
4. 한 번 기록한 답은 바뀌지 않는다. 답 1건의 이력·진행도 기록은 단일 트랜잭션이다 (REQ-106).
5. 출제 규칙: 퀴즈는 활성 단어장 단어가 4개 미만이면 거부하고 (D7), 오답 보기는 같은 단어장에서 우선 뽑고 부족하면 전체에서 보충한다 (D8). 단어 선별은 워터폴이다 (오답 ≤30%, 복습 10% 선확보, 나머지 미학습, 부족 시 복습 충원).
6. 숙련은 연속 정답 3회, 오답 1회면 연속 0·숙련 해제 (D17).

### 대안 (사후 정리)
| 대안 | 장점 | 단점 | 판정 |
| :--- | :--- | :--- | :--- |
| 클라이언트가 정답을 알고 채점 | 서버 왕복이 줄어든다 | 개발자 도구로 정답이 보인다. 기록 신뢰도가 낮다 | 기각 |
| 세션을 서버 메모리에 보관 | 구현이 단순하다 | 재시작에 소실, 멀티 워커 비공유 (ADR-001 과 같은 이유) | 기각 |
| **DB 스냅샷 + 서버 채점** | 재시작 후에도 유지, 멱등 기록, 시드가 바뀌어도 진행 중 세션 불변 | 문항마다 서버 왕복이 필요하다 | **채택** |

### 결과
- 출제 응답에서 정답을 숨기므로 채점 전에 정답을 알 수 없다. 플래시카드는 정답 개념이 없고 뜻이 문항에 포함된다 (카드 뒷면에 필요).
- 진행 중인 세션을 다시 조회하는 API 가 없어 새로고침하면 이어갈 수 없다 (Architecture Design A6). 푼 문항은 이미 기록된다.
- 만료된 `quiz_sessions` 의 물리 삭제 배치가 없다 (Data Design F4).
- **README §7 의 "퀴즈 출제 응답에는 정답 인덱스가 포함됩니다" 서술은 현재 코드와 맞지 않는다.** README 정정이 필요하다 (이 ADR 의 근거는 코드와 D16).

## ADR-006. 간격 반복(SRS): 6단계 간격표, 오답 부분 감쇠

- **상태**: Accepted — 1~3단계(알고리즘·스키마·답 기록 연동)와 4단계(출제 풀 연동, `source=due` 세션, 복습함 카드)를 모두 구현했다 (2026-11-19 반영). **사후 기록**: 근거는 `ai-agent/claude/작업계획_261111_SRS_복습_알고리즘.md`.
- **관련 요구사항**: REQ-150 (이슈 #25). Requirement Spec v2.2 에 반영했다.

### 배경
- 기존 숙련 규칙(연속 정답 3회)만으로는 "언제 다시 볼지"를 정하지 못한다. 망각곡선에 맞춘 복습 시점이 필요하다 (Data Design F2).

### 결정
1. 단계 0~5, 간격은 0·1·3·7·14·30일 (`services/srs.py` 의 `INTERVAL_DAYS`).
2. 정답은 1단계 상승, 오답은 **2단계 하락(부분 감쇠, 최소 0)**. 이미 오래 기억한 단어를 한 번 틀렸다고 처음부터 외우게 하지 않기 위해서다. 감쇠 폭은 상수 `WRONG_STEP_PENALTY` 로 조정한다.
3. 계산은 DB·시계에 의존하지 않는 순수 함수 `schedule_next(step, is_correct, now)` 다.
4. `user_word_progress` 에 `interval_step`, `next_review_at` 과 인덱스 `(user_id, next_review_at)` 를 둔다. 기존 행은 연속 정답 수(최대 5)로 단계를 백필한다.
5. `is_memorized` 는 SRS 단계로 흡수하지 않는다. 숙련 단어도 기한이 되면 복습 풀로 돌아온다 (복습 시각이 없는 옛 숙련 단어는 되살리지 않는다).
6. **출제 연동(4단계)**: `source=all` 의 복습 슬롯은 기한이 지난 단어를 오래 밀린 순으로 먼저 쓴다. `source=due` 세션은 기한이 도래한 단어만으로 만들고, 통계 응답에 `due_review_count` 를 싣는다.
7. **다음 복습 시각은 간격일 뒤 한국 날짜의 0시다** (2026-11-19 사용자 확정). 답한 시각 + 간격이면 밤 11시에 맞힌 단어가 다음 날 오전에 열었을 때 아직 기한 전이 된다. 날짜 0시로 맞추면 그 날 하루 종일 "오늘 복습"에 뜬다. 단계 0(오답)은 오늘 0시라 즉시 복습 대상이다.
8. **기한 전에 맞힌 정답은 단계와 복습 시각을 바꾸지 않는다** (2026-11-19 사용자 확정). 정답 수·연속 정답·숙련은 평소대로 쌓는다. 오답은 기한과 무관하게 단계를 내린다. 같은 날 여러 번 풀어 단계가 부풀면 (실측: 30분 사이 3번 정답 → 단계 3, 7일 뒤) 망각곡선의 취지에 어긋난다.

### 대안 (사후 정리)
| 대안 | 장점 | 단점 | 판정 |
| :--- | :--- | :--- | :--- |
| 오답 시 0단계 완전 리셋 | 구현이 가장 단순하다 | 오래 기억한 단어도 처음부터 반복해 학습 부담이 크다 | 기각 (부분 감쇠를 사용자가 승인) |
| SM-2 등 계수 기반 알고리즘 | 단어별 난이도를 반영한다 | 단어별 계수 컬럼과 튜닝이 필요하다. 지금 데이터량에서 이득이 불확실하다 | 보류 (작업계획서에 비교 기록 없음, 필요 시 재검토) |
| 기한 전 정답도 단계 상승 (최초 구현) | 구현이 가장 단순하다 | 같은 날 반복 학습으로 단계가 부풀어 복습이 7일 뒤로 밀린다 | 기각 (결정 8) |
| 복습 시각 = 답한 시각 + 간격 (최초 구현) | 구현이 단순하다 | 늦은 밤에 맞힌 단어가 다음 날 오전에 기한 전이 된다 | 기각 (결정 7) |
| **고정 간격표 + 부분 감쇠** | 단순하고 예측 가능하며 순수 함수로 테스트하기 쉽다 | 단어별 난이도를 반영하지 못한다 | **채택** |

### 결과
- 간격표와 감쇠 폭은 코드 상수라 조정이 쉽다. 값을 바꾸면 기존 사용자의 다음 복습 시각이 새 규칙과 어긋날 수 있다.
- 4단계 반영으로 ADR-005 의 워터폴 복습 슬롯이 기한 지난 단어를 먼저 쓰게 되었다. 풀 구성 규칙을 바꿀 때는 이 ADR 과 ADR-005 를 함께 갱신한다.

## ADR-007. 빌드 없는 Vanilla JS 프론트엔드, 같은 출처 서빙

- **상태**: Accepted. **사후 기록**: 프로젝트 지침(`CLAUDE.md` §1)이 정한 제약이며 결정 당시의 대안 비교 문서는 없다.
- **관련 요구사항**: REQ-116, REQ-114, REQ-115, `CLAUDE.md` §1, §4-6

### 결정
1. 프론트엔드는 HTML5, Vanilla JavaScript(ES 모듈, JSDoc), Tailwind CSS(Play 스크립트), SweetAlert2, Lucide 로 구성하고 **빌드 파이프라인을 두지 않는다.**
2. FastAPI 가 같은 프로세스에서 정적 파일을 `/` 에 마운트해 서빙한다 (같은 출처).
3. DOM 이 없는 순수 로직은 `js/core/` 에 두어 `node --test` 로 외부 패키지 없이 검증한다.
4. 화면은 `innerHTML` 없이 `textContent` 로 렌더링한다.
5. (2026-11-24) 외부 라이브러리·폰트는 CDN 이 아니라 `src/frontend/vendor/` 에 버전 고정 파일로 두고 같은 출처로 서빙한다. 출처·버전·라이선스는 `vendor/README.md` 에 기록하며, 앱 소스에 외부 URL 이 들어오면 `tests/self-hosted.test.js` 가 실패한다.
6. (2026-11-25) 정적 서빙: `vendor/` 응답에만 `Cache-Control: public, max-age=31536000, immutable` 을 붙이고(경로에 버전이 있어 바뀌면 경로도 바뀐다), `app.js`·`app.css` 는 ETag 재검증을 유지한다. woff2 MIME(`font/woff2`)은 OS `mime.types` 가 없는 컨테이너에서도 호스트와 같도록 앱이 직접 등록한다.

### 대안 (사후 정리)
| 대안 | 장점 | 단점 | 판정 |
| :--- | :--- | :--- | :--- |
| React/Vue + 번들러 | 컴포넌트·상태 관리 생태계 | 빌드 도구, npm 의존성, 별도 개발 서버가 필요하다 | 기각 (지침이 금지) |
| 프론트 별도 서버(Nginx 등) | 정적 자원 캐시·분리 | CORS·쿠키 설정, 컨테이너 추가 | 기각 (같은 출처가 ADR-001 쿠키 인증과 맞는다) |
| **Vanilla JS + vendor 자체 호스팅 + FastAPI 정적 마운트** | 도구가 없어 단순하다. 오프라인·CDN 장애와 무관하다. 쿠키 인증이 자연스럽다 | 저장소가 약 4MB 커진다. 라이브러리 업데이트를 수동으로 한다. 상태 관리를 직접 한다 | **채택** |

### 결과
- CDN 의존은 해소했다 (Architecture Design A4). 다만 Tailwind Play 스크립트는 프로덕션 사용이 권장되지 않으므로, 성능 문제가 생기면 standalone CLI 로 정적 CSS 를 생성하는 방안을 별도 결정으로 검토한다 (지침 `CLAUDE.md` §1 과 충돌하므로 사용자 결정).
- 서체 파일이 실패해도 시스템 폰트로 폴백되도록 `--font-sans` 체인을 둔다 (UI/UX 설계서).

## ADR-008. 로그인 시도 제한을 프로세스 메모리에서 관리

- **상태**: Accepted (단일 프로세스 한정). **사후 기록**: 근거는 REQ-121 본문과 `core/rate_limit.py` 의 docstring.
- **관련 요구사항**: REQ-121

### 결정
- 로그인 실패를 IP 또는 닉네임 기준으로 **1분 5회**까지 허용하고, 도달하면 비밀번호와 무관하게 429 와 `Retry-After` 로 거부한다. 성공하면 해당 계정의 실패 기록을 지운다.
- 상태는 프로세스 메모리의 슬라이딩 윈도우(`collections.deque`)에 둔다. 외부 저장소를 쓰지 않는다. 시계는 테스트에서 주입한다.

### 대안 (사후 정리)
| 대안 | 장점 | 단점 | 판정 |
| :--- | :--- | :--- | :--- |
| **프로세스 메모리** | 의존성이 없고 구현이 단순하다 | 재시작 시 초기화, 워커마다 한도가 따로 적용된다 | **채택** |
| DB 테이블 | 재시작·멀티 워커에서도 유지된다 | 로그인 실패마다 쓰기가 발생한다 | 보류 |
| Redis | 만료 관리가 쉽다 | 스택에 없는 컨테이너가 필요하다 (ADR-001 과 같은 이유) | 보류 |

### 결과
- 현재의 단일 프로세스 구성에서만 한도가 정확하다. 워커를 늘리면 공유 저장소로 교체해야 한다 (Architecture Design A1). 요구사항에도 "단일 프로세스 한정"으로 명시되어 있다.

## ADR-009. 앱 컨테이너화: 멀티스테이지 이미지, 최소 환경 주입, 개발용 override

> **v1.1 주석**: 결정 2(`migrate` 서비스 분리), 3(`mysql:3306`·`MYSQL_*` 주입), 6(`mysql` 호스트 포트)은 DB 서버가 사라져 **ADR-010 으로 대체**되었다. 멀티스테이지 구조, `env_file` 미사용, 개발용 override 마운트 원칙, `git clone` 전달은 유효하다. 컨테이너 사용자 uid 는 prod 가 1000 에서 10001 로 바뀌었다.

- **상태**: Accepted (2026-11-25, 사용자 확정: HTTPS 제외, git clone 전달, DB 포트 loopback)
- **관련 요구사항**: REQ-116, REQ-117, REQ-152, REQ-112

### 배경
- 앱이 호스트 `.venv` 에서만 실행되어 다른 PC 에서 같은 환경을 재현할 수 없었다 (Architecture Design A2).
- 사용자는 개발 환경까지 컨테이너로 옮기고, HTTPS 없이 사내망의 다른 PC 에서 실행하길 원했다.

### 결정
1. 하나의 `docker/Dockerfile` 에 `base`(공통 의존성) → `dev`(테스트 도구, 소스 마운트) / `prod`(소스 복사, 헬스체크)를 둔다. `python:3.12-slim`, 비root `app`(uid 1000).
2. 마이그레이션은 앱 시작과 분리한다. `migrate` 서비스가 `alembic upgrade head` 를 1회 실행하고, `app` 은 `service_completed_successfully` 뒤에 시작한다.
3. 앱·migrate 에는 `env_file` 을 쓰지 않고 필요한 변수만 `environment` 로 주입한다. 컨테이너 안의 DB 주소는 `mysql:3306` 으로 고정한다. `MYSQL_DATABASE/USER/PASSWORD` 는 `${VAR:?메시지}` 로 누락 시 중단한다.
4. 개발용 override(`docker-compose.dev.yml`)는 `./src` 와 테스트가 읽는 파일만 마운트한다. 저장소 전체와 `.env` 는 마운트하지 않는다.
5. 전달 방식은 **`git clone` 후 현지 빌드**, HTTP 전용(사내망·LAN, `COOKIE_SECURE=false`)이다. 이미지 레지스트리와 HTTPS 는 도입하지 않는다.
6. `mysql` 의 호스트 포트는 `127.0.0.1` 에만 연다. 앱은 내부 네트워크로 접속한다.

### 대안
| 대안 | 장점 | 단점 | 판정 |
| :--- | :--- | :--- | :--- |
| `env_file: .env` 로 통째 주입 | 설정이 간단하다 | 루트 비밀번호와 호스트용 `MYSQL_HOST=127.0.0.1`·`MYSQL_PORT=3307` 이 앱 컨테이너로 들어가 DB 주소를 덮어쓴다 | 기각 |
| 앱 시작 때 마이그레이션 자동 실행 | 서비스가 하나 줄어든다 | 인스턴스가 늘면 마이그레이션이 경합하고, 실패 원인이 앱 로그에 섞인다 | 기각 |
| 저장소 전체를 dev 컨테이너에 마운트 | 설정이 가장 단순하다 | `.env`(루트 비밀번호)가 컨테이너에 노출된다 | 기각 |
| 이미지 레지스트리(GHCR 등) 또는 `docker save` | 소스 없이 실행, 오프라인 가능 | 계정·절차가 늘고 현재 규모에 과하다 | 보류 (필요 시 추가) |
| 리버스 프록시 + HTTPS | 비밀번호 보호, 인터넷 공개 가능 | 인증서·컨테이너가 늘고 이번 범위 밖이다 | 보류 (A10) |
| **멀티스테이지 + migrate 분리 + 최소 environment** | 재현성·보안·빌드 캐시 효율 | 이미지 빌드가 필요하다 | **채택** |

### 결과
- 호스트에 Python 이 없어도 개발·테스트가 된다 (컨테이너 안 백엔드 전체 pytest 통과 확인). 이미지는 개발용 약 375MB, 배포용 약 360MB 이다.
- 새 PC 는 빈 DB 로 시작하므로 사용자·학습 기록 이전은 수동이다 (Architecture Design A11, README §3.8).
- HTTP 전용이므로 인터넷에 공개할 수 없다 (Architecture Design A10).
- `Settings` 가 환경 변수를 `.env` 보다 우선하므로 컨테이너에는 `.env` 가 없어도 된다.

## ADR-010. DB 를 MySQL 에서 SQLite 로 전환, `BEGIN IMMEDIATE` 로 쓰기 직렬화

- **상태**: Accepted (2026-11-25, 사용자 확정: SQLite 채택, 과제용은 빈 DB, PostgreSQL 협의는 하지 않음)
- **관련 요구사항**: REQ-108, REQ-116, REQ-117, REQ-152, REQ-153 (VOCA-NFR-002, 003, 005)

### 배경
- 기말과제 서버 규칙: DB 는 SQLite 만 쓴다(PostgreSQL 17 은 사전 협의 시만, MySQL 등은 불가). 컨테이너는 UID 10001, 쓰기는 `/data`·`/tmp` 만, 메모리 1GB, 실행 중 인터넷 차단이다.
- 기존 구현은 MySQL 8 전용 구문(`ON DUPLICATE KEY UPDATE`, `SELECT ... FOR UPDATE`, `INTERVAL 9 HOUR`, 콜레이션 `utf8mb4_0900_ai_ci`, `mysql.*` 컬럼 타입, 12개 마이그레이션)에 의존했다.

### 결정
1. **SQLite 단일 파일 DB**(`DB_PATH`, 기본 `/data/voca.db`)와 드라이버 `aiosqlite` 를 쓴다. MySQL 이중 지원은 하지 않는다.
2. 과제용은 **빈 DB 에서 시작**한다. 기존 MySQL 데이터는 이관하지 않는다.
3. MySQL 리비전 12개를 SQLite 초기 리비전 `0001` 하나로 재작성한다(`render_as_batch=True`). 컨테이너는 시작할 때 `alembic upgrade head` 를 실행한다(`docker-entrypoint.sh`).
4. 연결마다 `foreign_keys=ON`(CASCADE 동작에 필수), `journal_mode=WAL`, `synchronous=NORMAL`, `busy_timeout=5000` 을 건다.
5. **모든 트랜잭션을 `BEGIN IMMEDIATE` 로 시작**한다. 행 잠금(`FOR UPDATE`)의 대체이며, 쓰기가 한 번에 하나씩 순서대로 처리된다.
6. 대소문자 무시 유일성은 `COLLATE NOCASE`(닉네임, 표제어, slug)로 둔다. 악센트 무시는 시더의 자체 정규화가 맡는다.
7. upsert 는 `INSERT ... ON CONFLICT DO NOTHING`, KST 일자는 `date(col, '+9 hours')`, 무결성 오류는 제약 이름이 아니라 `테이블.컬럼`(유니크)과 메시지(외래키)로 판별한다(`db/errors.py`).

### 대안
| 대안 | 장점 | 단점 | 판정 |
| :--- | :--- | :--- | :--- |
| MySQL 유지 | 코드 변경 없음 | 과제 규칙상 불가 | 기각 |
| PostgreSQL 17 | 행 잠금·콜레이션 유지 가능 | 사전 협의 필요, 방언 전환 비용이 SQLite 와 비슷 | 기각 |
| SQLite + MySQL 이중 지원 | 개발 환경 유지 | 방언 분기와 테스트가 두 배 | 기각 |
| 기본 `BEGIN`(DEFERRED) | 읽기 요청이 잠금을 잡지 않음 | 읽기 후 쓰기 승격 시 다른 커밋이 끼면 `busy_timeout` 과 무관하게 즉시 `database is locked` (인증이 먼저 읽으므로 실제 발생. 테스트로 재현) | 기각 |
| **SQLite + WAL + `BEGIN IMMEDIATE`** | 외부 서버 불필요, 쓰기 직렬화로 동시 기록 정확 | 읽기 요청도 쓰기 잠금을 잠깐 잡고, 다중 쓰기 서버로 확장할 수 없다 | **채택** |

### 결과
- DB 컨테이너가 사라져 compose 는 `app` 하나가 되고, 테스트는 임시 SQLite 파일(마이그레이션 적용)로 Docker 없이 전체가 돈다(667건, 약 40초).
- 동시 기록 20건이 유실 없이 집계됨을 `test_sqlite_services.py` 가 검증한다. 읽기 후 쓰기 승격 실패는 같은 파일의 테스트가 재현한다.
- 컨테이너 기동은 시드 1,000단어 적재를 포함해 약 4초이고, 점검 워크플로(30초 이내 응답)를 통과한다.
- 단일 프로세스·단일 컨테이너가 전제다. 워커를 늘리면 쓰기 경합이 생긴다(ADR-008 의 한도 제한과 같은 전제).
- 악센트 무시 유일성이 사라졌다. 현재 시드에는 악센트가 있는 표제어가 없다.

## ADR-011. 고정 `admin` 관리자 계정과 코드에 둔 초기 비밀번호

### 배경
단어 관리 기능(과제 VOCA-FR-001~003)은 관리자 전용으로 정했다. 채점 환경에서 별도 설정 없이 관리자로 로그인할 수 있어야 한다.

### 결정
1. 관리자는 닉네임 `admin` 계정 하나다. 역할 컬럼은 두지 않고 닉네임으로 판정한다 (`core/admin.py`). 닉네임 변경 기능은 없다.
2. 서버 시작 때 계정이 없으면 초기 비밀번호 `admin1234` 로 만든다. 있으면 건드리지 않는다.
3. `admin` 닉네임은 일반 가입에서 예약하고, 관리자 탈퇴는 거부한다 (지우면 초기 비밀번호로 다시 생기기 때문이다).
4. 관리자는 마이페이지에서 비밀번호를 바꾼다 (REQ-164).

### 대안
| 대안 | 장점 | 단점 | 판정 |
| :--- | :--- | :--- | :--- |
| `ADMIN_USERNAME` 환경 변수 (2026-11-25 안) | 코드에 비밀값 없음 | 계정 선점 위험, 채점 환경 설정 필요 | 기각 |
| `ADMIN_INITIAL_PASSWORD` 환경 변수 | 코드에 비밀값 없음 | 값을 넣지 못하는 환경에서는 관리자 기능을 쓸 수 없음 | 기각 |
| **코드 상수 초기 비밀번호** | 설정 없이 바로 로그인, 스키마 변경 없음 | 공개 저장소에 값이 노출됨 | **채택** (사용자 결정) |

### 결과
- CLAUDE.md §5.3(비밀값 하드코딩 금지)과 VOCA-NFR-004(비밀값은 환경 변수)의 예외다. 요구사항 명세 §11 에 🟡 로 적는다.
- 배포 직후 바꾸지 않으면 누구나 관리자로 로그인해 단어를 고치거나 지울 수 있다. 배포 절차에서 첫 로그인과 비밀번호 변경을 먼저 한다.
- 기존 DB 에 이미 `admin` 닉네임 계정이 있으면 그 계정이 관리자가 된다.

## ADR-012. 표준 콘텐츠에 출처 컬럼을 두고 관리자 등록분과 공존

### 배경
관리자는 새 단어장과 기존 표준 단어장 양쪽에 단어를 넣을 수 있어야 하고(사용자 결정), 시드 로더는 서버 시작마다 표준 콘텐츠를 DB 에 맞춘다 (ADR-004). 두 쓰기 경로가 같은 테이블을 만진다.

### 결정
1. `system_vocabularies`, `system_words` 에 `source`(`seed`|`admin`) 컬럼을 둔다. 학습·출제·통계 코드는 그대로 쓴다.
2. 마이그레이션은 `ADD COLUMN` 만 쓴다. batch 재작성은 `COLLATE NOCASE` 소실과 학습 이력 연쇄 삭제 위험이 있다. 값 제한은 CHECK 대신 앱이 한다.
3. 표제어가 겹치면 **시드가 우선**한다. 행 id 를 유지해 학습 이력을 보존하고 `source` 를 `seed` 로 바꾼다.
4. 시드 콘텐츠는 관리 API 로 수정·삭제할 수 없다. 고쳐도 시드 파일이 바뀌면 덮어써지기 때문이다.

### 대안
| 대안 | 장점 | 단점 | 판정 |
| :--- | :--- | :--- | :--- |
| 관리자 전용 테이블 | 시드와 충돌 없음 | 조회·출제·통계·북마크가 두 벌 | 기각 |
| 모든 단어 수정·삭제 허용 | 관리 자유도 | 시드 덮어쓰기를 막는 변경 표시·숨김 설계가 필요 | 기각 (사용자 결정: 관리자 등록분만) |
| **출처 컬럼** | 구조 변화가 작고 기존 데이터 보존 | 시드와 겹치면 관리자 입력이 덮어써짐 | **채택** |

### 결과
- 단어 삭제는 모든 사용자의 해당 이력·진도·북마크를 지운다. 화면에서 확인을 받는다.
- 표준 단어장에 더한 단어는 목록 끝에 붙어, 미학습 출제에서는 기존 단어 뒤에 나온다.

## ADR-013. CSV 를 원문 본문으로 받고, 받는 동안 쓰기 잠금을 놓는다

### 배경
모든 트랜잭션이 `BEGIN IMMEDIATE`(ADR-010)라 권한 확인 조회만으로 SQLite 쓰기 잠금을 잡는다. 그 상태에서 파일 본문을 받으면 느린 업로드가 끝날 때까지 다른 사용자의 쓰기가 멈추고, 대기 시간(5초)을 넘으면 실패한다.

### 결정
1. `multipart` 가 아니라 `text/csv` 원문을 받는다 (`python-multipart` 의존성이 필요 없다).
2. 권한을 확인한 뒤 `commit` 해 잠금을 놓고, 상한까지만 본문을 읽는다.
3. 파싱·검증(`services/csv_import.py`, DB 없음)을 모두 마친 뒤 새 트랜잭션 하나로 저장한다.

### 대안
| 대안 | 장점 | 단점 | 판정 |
| :--- | :--- | :--- | :--- |
| `multipart` 업로드 | 일반적인 파일 업로드 방식 | 의존성 추가, 본문을 읽는 시점을 다루기 어렵다 | 기각 |
| 화면에서 CSV 를 JSON 으로 바꿔 전송 | 기존 JSON API 형식 | 파싱·검증 규칙이 서버와 화면 두 곳에 생긴다 | 기각 |
| **원문 본문 + 잠금 해제 후 읽기** | 의존성 없음, 잠금이 저장 구간으로 한정 | 라우터가 본문 상한을 직접 지킨다 | **채택** |

### 결과
- 잠금 해제를 빼면 `test_a_slow_upload_does_not_block_other_writes` 가 실패한다.
- 본문을 받는 사이 단어장이 지워지면 404 다.

## ADR-014. 일차는 학습량 달성으로 넘기고 학습 이력에 저장한다

### 배경
과제는 "하루 학습량(단어 수)에 따라 1일차, 2일차 … 진도"를 만들고 "몇 일차"를 DB 에 남기라고 한다. 일차를 날짜와 학습 회차 중 무엇으로 세는지는 정하지 않았다.

### 결정
1. 학습량(`daily_goal`)만큼 서로 다른 단어를 풀고 한국 날짜가 바뀌면 다음 일차다 (사용자 결정).
2. `study_logs.study_day` 한 컬럼에 저장한다. 사용자별·단어장별로 센다.
3. 쓰기와 화면이 같은 함수(`services/study_day.py` 의 `current_day`)를 쓴다.

### 대안
| 대안 | 장점 | 단점 | 판정 |
| :--- | :--- | :--- | :--- |
| 학습한 날의 순번 | 규칙이 단순 | 학습량과 무관해 "학습량에 따라"를 충족하기 어렵다 | 기각 |
| 계산만 하고 저장하지 않음 | 스키마 변경 없음 | DB 에서 확인하는 항목(VOCA-FR-014)을 충족하지 못한다 | 기각 |
| 일차 진도 테이블 | 넘어갈 때의 학습량까지 보존 | 테이블과 동기화가 늘어난다 | 기각 |
| **이력 컬럼 + 학습량 달성** | 구조 변화가 작고 두 요건을 직접 충족 | 아래 결과의 제약 | **채택** |

### 결과
- 설정을 바꾸면 이후 판정에 새 학습량이 쓰인다.
- 답 1건마다 조회가 늘지만 사용자·단어장 범위라 작다.
- 관리자가 단어를 지우면 이력이 함께 지워져 일차의 단어 수가 줄 수 있다.
